# Secure MOM contracts

**Contract version:** `1.0`  
**Status:** proposed app boundary; Affan's artifact format and handoff trigger are pending confirmation.

`meeting.schema.json` is a JSON Schema Draft 2020-12 document. Its top level is a **fixture bundle** showing each record shape together; it is not an API response wrapper. Reuse definitions under `$defs` for individual API payloads. `fixtures/meeting.json` uses synthetic IDs and text. `fixtures/final-document.html` is the proposed UTF-8, self-contained HTML output for discussion with Affan.

## Records

| Schema definition | Purpose |
|---|---|
| `organization` | Organization scope identifier |
| `patient` / `patientLink` | Minimal directory record and explicit operator-created association |
| `meeting` | Metadata, linked records, lifecycle and current transcript revision |
| `asset` | Source media metadata and opaque local storage key |
| `segment` | Original timed transcript text and revision |
| `action` / `evidence` | Decision state, nullable owner/date and separate supporting quotes |
| `job` | Durable work state and frozen profile/model configuration |
| `reviewIssue` / `transcriptEdit` | Bounded review span and immutable revision edit |
| `artifact` | Final file identity, snapshot revision, digest and readiness state |
| `error` | Stable machine code, safe message, retryability and request ID |

IDs are opaque within their owning organization. All times are RFC 3339 timestamps with an explicit offset; transcript offsets are integer milliseconds from the original asset. Review offsets are Unicode code-point offsets with half-open `[startOffset, endOffset)` ranges. Preserve transcript Unicode verbatim. Null means unknown or not supplied; do not replace it with a guessed value.

Patient association is explicit and does **not** grant access. A meeting may have zero or multiple patient links. The service must independently authorize every referenced object and filter access before search, counts, pagination, media and exports.

## Validation rules beyond JSON Schema

JSON Schema checks each record's shape and local constraints. The service must additionally check:

- Every referenced organization, patient, patient link, meeting, participant, asset, segment, job, artifact and edit exists and belongs to the same authorized scope.
- A patient link's `meetingId`/`patientId` agree with the meeting's `patientLinkIds`; links are human-created, never inferred from names.
- `startMs < endMs`, end times fit inside the referenced asset, and cited evidence segment/revision exists. Its quote must match the cited text and offsets.
- Action task, owner and date evidence are validated separately. A null owner/date stays unresolved; its evidence array is empty.
- Review/edit offsets address the exact original text for that transcript revision. Reject stale revisions, mismatched substrings and overlapping batch edits. A new edit creates a new revision.
- Artifact SHA-256 is computed from the exact file bytes. `ready` is published only after an atomic write and only for the current snapshot. A changed snapshot marks previous artifacts `superseded` or `revoked`.
- Storage keys are generated by the service, remain inside the configured data root, and contain no patient names or uploaded filenames. Do not treat them as arbitrary filesystem paths.
- A ready artifact means only that our file is complete. It does not mean Affan accepted or sent it.

The JSON Schema `format` keyword is annotation unless a validator enables format assertion; API validators should explicitly parse date-time values. JSON Schema cannot verify cross-record references, source bounds, authorization or the digest-to-file match.

## API examples for consumers

These are interface examples, not a claim that routes exist yet. Freeze exact route and response naming when implementing the service.

```http
POST /api/meetings
Content-Type: application/json
```

```json
{
  "contractVersion": "1.0",
  "title": "Synthetic meeting",
  "recordedAt": "2026-09-26T09:00:00Z",
  "timeZone": "Europe/Chisinau",
  "outputLanguage": "en",
  "patientLinkIds": []
}
```

Expected validation error shape:

```json
{
  "code": "INVALID_REQUEST",
  "message": "The meeting request is invalid.",
  "retryable": false,
  "requestId": "request-demo-002",
  "details": { "field": "outputLanguage" }
}
```

The message and `details` must not echo sensitive transcript text or patient data. Authenticated endpoints also return a non-enumerating not-found/denied result when disclosure of another organization's record could leak its existence.

## Artifact boundary with Affan

The fixture proposes self-contained HTML with print styles and `text/html; charset=utf-8`. Its manifest identifies artifact, meeting, snapshot revision, opaque storage key, media type, SHA-256, status and creation time. No recipient, email, queue, retry or transport fields belong here. **Affan must confirm file format and how/when he consumes the file; until then HTML and the local ready-artifact interface remain proposals.**

Files are generated without patient names in their storage paths. The renderer must escape all transcript-derived content and include only the patient details needed for the explicitly authorized use. The synthetic fixture is not a clinically suitable template.

## Versioning

Contract version applies to this bundle; persisted records also carry their own data revisions where edits can change meaning. Add optional fields compatibly. A breaking field/meaning change requires a new contract version and migration plan; never reinterpret an existing transcript or artifact revision in place. Keep old fixtures so downstream consumers can validate migration behavior.
